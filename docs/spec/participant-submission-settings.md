# Participant submission settings

`SubmissionSettingsPage` supports a read-only participant presentation. It is selected by `participantAuthenticationRequired: true` or by the current loaded snapshot's `participantAuthentication` declaration. The optional hint describes presentation policy; it does not change native configuration, acquire credentials, log in, restore a session, confirm consent or grant permission. Core retains all actual authentication, destination trust, credential and server authorization decisions.

The participant page uses the App title **送信設定** and displays:

> アカウントでログインして送信します。送信先は担当者が管理します。

Operators provision the authority and trusted delivery destinations through Core's configuration responsibility. Participants use the ordinary shared Account login page. The compact page exposes no default selectors, Drive/HTTP editors, connection/account/folder/endpoint forms, bearer writers, native authorization controls, raw connection/profile IDs or URLs. Actual meaningful delivery destinations and transfer observations remain on their existing status surfaces. This is presentation policy, not a new operator console or a security boundary against direct Core callers.

Configuration state remains literal. An unloaded owner says it is not loaded; a pending read shows loading; failures use the existing fixed safe messages. A successfully loaded snapshot without a participant declaration or selected transport says **送信先を準備中です。担当者に確認してください。** It does not claim readiness or a login grant. Explicit **再読み込み** remains an ordinary configuration read, independent of the technical mutation guard, and performs no token read or scheduling.

When an Account callback is supplied, **アカウントを開く** invokes only the current mounted, attached, idle owner's callback on explicit intent. An absent callback produces no dead button. Building the page never invokes it. The App borrows the root's existing Account opener only while its authentication facade is present and open. The settings wrapper captures its exact route/runtime/generation, rejects covered or retired routes and duplicate intent, pops that settings route, then invokes and observes the borrowed opener. Account login can therefore retire the root submission runtime without leaving a closed settings route underneath Account. Ordinary Back returns to the retained Home route. Navigation failures publish no late settings state.

Settings owns its controller and detachment join; root owns submission resources, while the Account facade retains its existing owner. Pending accepted configuration reads drain before owned resources close. Settings never closes the borrowed Account facade. Account input/result follows the existing shared Account page/client lifecycle; Book documents, photo originals and audio histories remain untouched.

Legacy false/null mode preserves the full technical form and existing capability bindings. Every technical callback also rechecks the *current* participant policy at invocation, including callbacks captured before a mode change, controller replacement or detach. Hiding widgets alone is insufficient. Already dispatched operations retain their existing native effect and drain semantics; changing presentation does not cancel or rewrite them.

Executable host specifications in `test/participant_submission_settings_test.dart` cover explicit required mode, stored v3 mode, missing declarations/transport, loading/failure/unloaded state, explicit navigation/reload, retained legacy capabilities and stale technical callbacks. The App's `test/participant_submission_account_navigation_test.dart` covers real root/settings/Account navigation, route reservation and retirement, borrowed facade state, read draining and retained local data. Controlled host ports prove presentation and UI ownership only.
